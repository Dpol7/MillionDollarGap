IMPORTANT CORRECTION TO THE BLOCK MAP:

The current visualization is getting the dots wrong.

The dots are NOT decorative particles and they are NOT an approximation of the number of blocks.

The visualization must represent a real one-to-one mapping between Bitcoin block heights and dots.

CORE RULE:

ONE DOT = ONE BLOCK HEIGHT.

If the prediction range contains 526,001 block heights, the underlying visualization must represent exactly 526,001 unique blocks.

Every block must have a deterministic identity.

Example:

Block #1,100,000 = one dot

Block #1,100,001 = one dot

Block #1,100,002 = one dot

...

Block #1,626,000 = one dot

There must be no duplicated blocks and no missing blocks.

DO NOT simply generate a random particle field.

DO NOT generate a visually approximate number of dots.

DO NOT use random positioning.

DO NOT use random spacing.

The visualization should be generated algorithmically from block height.

==================================================
VISUAL LAYOUT
==================================================

Because hundreds of thousands of dots cannot reasonably fit on one screen individually, use a deterministic grid/timeline layout.

For example:

Block #1,100,000
Block #1,100,001
Block #1,100,002
Block #1,100,003
...

Each block gets a sequential position in the visualization.

The visual position should be calculated from:

index = block_height - start_block

The block's position should then be:

column = index % BLOCKS_PER_ROW

row = floor(index / BLOCKS_PER_ROW)

This means every block has exactly one location.

DO NOT randomly position dots.
